数字人阶段1：实时语音输出模块

发表于2026-10-21|更新于2026-10-21|编程
|字数总计:6.3k|阅读时长:22分钟|阅读量:

这是数字人盒子第一阶段的阶段汇报，主题是低档盒子基座 TTS 的模型选型、RTF 基准与端侧优化路线。

服务器上 MeloTTS 的中长句已稳定快于实时（RTF≈0.47）；但按算力外推，RK3566 约 2.3–3.4、RK3528 约 3.4–5.3，都无法直接用当前 163 MiB 的 fp32 模型实时运行。必须走「轻量模型 + 降采样率 + 流式按句 + 量化 / 运行时优化」的组合路线。

数据口径：文中标注【实测】的为服务器真实测量；【外推】为基于 CPU 规格的工程估算，不是真机结果；【建议】为待评审的下一步方案。所有端侧结论必须在 RK3566 / RK3528 物理盒子上用同一套脚本复测，才能作为定论。

项 内容
测试模型 vits-melo-tts-zh_en（MIT，单女声，中英混合，44.1 kHz，163 MiB fp32）
测试引擎 sherpa-onnx 1.13.8 + onnxruntime 1.31.0，CPUExecutionProvider
测试口径 4 核 / 4 线程 / fp32，15 条不同长度句子

一、结论摘要

1.1 关键数字一览

首音延迟（16 字首句） 1.26 s 6–9 s 9–14 s ≤1.5 s
峰值内存 436 MB — — ≤200 MB

1.2 议题与结论

议题 结论
模型选择 选用 vits-melo-tts-zh_en：MIT 许可、单女声、中英混合、44.1 kHz、163 MiB fp32。许可干净、音质好、sherpa-onnx 官方支持；缺点是模型偏大，不适合作为 RK3528 的最终形态。
服务器性能【实测】 15 句样本：中句 RTF 中位 0.470、长句 0.475、短句 0.524；首音延迟 1.26 s；峰值内存 436 MB；模型加载 3.04 s。中长句约为实时的 2.1 倍。
RK3566 外推【外推】 单核综合差距约 4–5 倍，理论 RTF 1.9–2.4，工程修正后 2.3–3.4；不能直接用 MeloTTS 实时，但优化后有机会做到 RTF≤0.5。
RK3528 外推【外推】 单核综合差距约 6–8 倍，理论 RTF 2.9–3.8，工程修正后 3.4–5.3；直接用 MeloTTS 远不能实时，必须换更轻的模型。
优化路线【建议】 按杠杆排序：换轻量模型 / 降采样率（最高杠杆）→ INT8 量化 → 运行时与后端优化 → 流式按句与预烘焙话术。单一手段不够，必须组合。
需要会议决策 首发硬件是否优先 RK3566；是否接受 22.05 / 16 kHz 的音质取舍；是否批准 2 周“轻量模型 + 真机验证”专项。

二、项目背景与本期目标

2.1 产品定位

数字人盒子是纯本地运行的“听 → 想 → 说”设备：

  • 低档（300–600 元）：ARM 纯 CPU、不启用 NPU（即使 SoC 自带 NPU），只做语音输出，使用预置音色，不做音色克隆。目标芯片为 RK3566 / RK3528 / S905X4 级别。
  • 高档（600–900 元）：ARM CPU + NPU，语音 + 数字人视频。

本期只针对低档盒子的基座 TTS（文字 → 普通话语音），不包含 ASR、音色克隆、数字人视频。

2.2 技术约束

  1. TTS 走“两段式”：第一段为轻量基座 TTS，第二段为独立音色转换器；本期只做第一段。
  2. 低档不做音色克隆，只用单说话人预置音色。
  3. 首发只保普通话，粤语作为后续候选。
  4. 允许流式输出，因此同时关心首音延迟和整体 RTF。
  5. 商用 IP 必须干净，只使用 MIT / Apache-2.0 等宽松许可的模型与代码。
  6. 核心逻辑与操作系统无关，采用 sherpa-onnx + ONNX，便于后续移植到 Android（官方提供 AAR/JNI）。

2.3 本期目标

  • 在 ARM 服务器上跑通基座 TTS 最小链路；
  • 建立可复现的 RTF / 首音延迟基准；
  • 估算 RK3566 / RK3528 的端侧可行性；
  • 给出把 RTF 压到实时线以下的优化路线。

三、模型选择（models/ 目录）

3.1 选型约束

约束 要求 对选型的影响
商用许可 MIT / Apache-2.0 等宽松许可 排除许可不明的 HF Space 转换模型
音色 预置、单说话人 多说话人模型也可用，但会增加体积，且对低档定位无收益
语言 普通话，兼顾中英混读 优先中文或中英双语模型
音质 会议/产品演示可接受 8 kHz 电话音质只能做轻量对照，不适合作为最终音色
体积/算力 低端 ARM 纯 CPU 可承受 模型越小、采样率越低越有利
工程生态 sherpa-onnx 官方支持 便于 Python 验证与 Android 复用同一套 ONNX

3.2 候选对比

说明：matcha-icefall-zh-baker、vits-piper-zh_CN 尚未下载和实测，仅作为下一轮候选；表中许可以包内 LICENSE 为准。

3.3 为什么选 vits-melo-tts-zh_en

  1. 许可干净：包内 LICENSE 为 MIT（Copyright 2024 MyShell.ai），允许商用、修改、分发，满足硬约束。
  2. 单说话人：README 明确“中文+英文 TTS 只有单一女声”，正好对应低档“预置音色、不克隆”的定位。
  3. 音质与采样率：44.1 kHz 输出，明显优于 8 kHz 的 aishell3，适合作为会议演示和音质基线。
  4. 官方支持：sherpa-onnx 官方预训练模型，Python/C++/Android 可复用同一套 ONNX，迁移成本低。
  5. 工程验证充分：最小链路、RTF 基准、端到端语音对话均已跑通。

它的定位是“音质/链路基线”，不是 RK3528 的最终模型。 163 MiB fp32 对几百元档盒子偏重，后续必须做轻量化；最终端侧模型将在 P0 轻量模型对比后确定。

3.4 models/ 目录清单

关键注意点：

  • 包内 model.int8.onnx 只有 133 字节，是占位 stub，不能用于推理；本次所有实测均使用 fp32 的 model.onnx。
  • 因此服务器上的 i8mm / bf16 INT8 加速并未生效；这也意味着本次数据是纯 fp32 的公平基线，与 A55/A53 的 fp32 推理更具可比性。
  • 模型目录合计约 183 MB，部署时需考虑 OTA 体积和存储占用。

3.5 许可结论

  • vits-melo-tts-zh_en：MIT，可商用。分发时需保留版权与许可声明。
  • vits-icefall-zh-aishell3：Apache-2.0，可商用，但 8 kHz 音质偏低。
  • vits-zh-hf-fanchen-C：许可来源不明，已排除。
  • 后续 Piper / Matcha 候选：必须逐个检查包内 LICENSE，尤其是 Piper 的部分音色为 CC-BY-NC，禁止商用。

四、RTF 基准结果【实测】

4.1 指标定义

  • RTF < 1 才可能实时；越小越好。
  • 首音延迟：流式场景下，从送入第一句文本到产出第一段音频的时间，直接决定用户“等多久听到第一声”。
  • 峰值 RSS：进程常驻内存峰值，决定低内存盒子能否承载。

4.2 测试方法

项 设置
样本 短句 5 条（6–7 字）、中句 5 条（18–26 字）、长句 5 条（64–86 字），共 15 条不同句子
重复 每条句子测 1 次；正式计时前全局预热 1 次，避免首句包含初始化开销
线程/核心 num_threads=4、OMP_NUM_THREADS=4、taskset -c 0-3（限 4 核）
精度 fp32（包内 int8 为占位 stub）
引擎 sherpa-onnx 1.13.8，onnxruntime 1.31.0，CPUExecutionProvider
统计 分类给出中位数、均值、最小、最大；另测长句首句的首音延迟

为什么改成“每类 5 句、每句 1 次”：早期用单一句子重复 5 次，容易对单句过拟合；15 条不同长度句子更能代表真实文本的波动。代价是单次测量会引入抖动，因此同时报告中位/均值/极值。

4.5 结果解读

  1. 中长句非常稳定：RTF 集中在 0.46–0.50，说明合成耗时基本随音频时长线性增长；服务器上约为实时的 2.1 倍，有约 50% 的 CPU 余量。
  2. 短句的 RTF 更高、波动更大：中位 0.524、均值 0.614，其中一条“好的，明白了。”达到 0.9686，逼近实时红线。原因有三个：
    • 短句存在固定的文本前端、FST、ONNX 调用开销，摊到 1 秒音频上更明显；
    • VITS 本身带随机噪声（noise_scale），同一句重跑也会有波动；
    • “每句只测 1 次”放大了单次调度抖动/离群点。
  3. 首音延迟 1.26 s：对服务器演示可接受，但对端侧是重要风险——用户对“第一声”的等待比整段 RTF 更敏感。
  4. 内存 436 MB：模型 163 MiB + onnxruntime/词法资源。对 1–2 GB 内存的低端盒子偏重，Android 系统本身还要占用内存。
  5. fp32 口径：本次未使用 INT8，服务器上的 i8mm/bf16 没有发挥作用；因此该结果是“服务器 fp32 上界”，对 A55/A53 的 fp32 推理更有参考意义，但服务器仍拥有更强的 IPC、缓存和内存带宽。
  6. 音频有效性：服务器没有声卡 PCM，无法真实播放；已通过 WAV 头、采样率、峰值、RMS、非零样本比例校验确认是真实语音，真机播放需在盒子上复测。

4.6 端到端链路验证（工程可行性）

在最小 TTS 链路上接入了阿里云百炼 qwen-flash（OpenAI 兼容接口），验证了“LLM 流式出字 + 本地按句 TTS + 顺序播放”的完整链路：

  • 终端输入 → 千问流式 token → 按 。！？； 切句 → TTS 合成 → 播放队列；
  • 回答文本与语音并行产出，合成快于播放，下一句在上一句播放期间已备好；
  • 实测首段音频延迟约 1.1–2.3 s（含模型出字 + 合成）；
  • 服务器无 /dev/snd PCM 设备，本次只验证了合成与队列，真实出声需在带声卡的盒子上运行。

结论：链路工程上已跑通；当前瓶颈是端侧算力，不是软件链路。

五、与 RK3566 / RK3528 的对比及理论 RTF

5.1 硬件规格对比

项 本实验服务器 RK3566 RK3528
CPU 4× Neoverse-N2 4× Cortex-A55 4× Cortex-A53
最高主频 3.0 GHz 1.8 GHz（RK3568 为 2.0 GHz） 约 1.5–1.8 GHz（公开资料口径不一，本文按 1.5 GHz 保守估算）
工艺 — 22 nm 28 nm
L3 缓存 64 MiB 无（共享 L2 较小） 无（共享 L2 较小）
NPU 无（纯 CPU） 约 0.8 TOPS INT8（RK3568 为 1 TOPS） 无
内存 7.2 GiB 通常 2–4 GiB LPDDR4/4X 通常 1–2 GiB LPDDR4/4X
ISA ARMv9，i8mm/bf16/SVE2 ARMv8.2，通常支持 dotprod，无 i8mm ARMv8.0，无 dotprod

说明：上表为公开规格与工程估算，不是同一台机器上的实测跑分。低档产品按纯 CPU 评估，RK3566 自带的 NPU 仅作为后续预研，不计入本期算力。RK3528 的主频在不同资料中差异较大，本文取 1.5 GHz 保守值；若实际为 1.8 GHz，外推结果可下调约 15%。

5.2 外推方法

在“同一模型、同一 fp32 精度、同样 4 线程、计算受限、无热降频”的假设下：

  • f：主频；
  • IPC：每时钟指令数，综合微架构与 NEON 吞吐；
  • η：内存带宽、缓存容量、线程扩展效率、热降频等工程修正，通常 1.2–1.4。

以服务器中长句 RTF 0.475 为基线，不同算力差距下的理论 RTF：

算力差距 k 3× 4× 5× 6× 7× 8× 10×
理论 RTF 1.43 1.90 2.38 2.85 3.33 3.80 4.75

5.3 理论 RTF 估计

平台 单核综合差距 k 理论 RTF（×0.475） 工程修正后（×1.2–1.4） 判断
RK3566（4×A55 @1.8 GHz） 4–5 1.9–2.4 2.3–3.4 不能直接用 MeloTTS 实时；优化后有机会
RK3528（4×A53 @1.5 GHz） 6–8 2.9–3.8 3.4–5.3 远不能实时；必须换更轻模型

若 RK3528 实际跑 1.8 GHz，理论 RTF 约 2.4–3.2，工程修正后约 2.9–4.4，结论不变：仍 >1。

若只按 4 核线性外推而忽略内存带宽/缓存差异，结果会偏乐观；低端 SoC 的共享 L2、内存总线和热设计都明显弱于服务器，实际可能比表中更差。

5.4 首音延迟外推

首音延迟与算力近似同比例放大。以服务器 16 字首句 1.26 s 为基线：

平台 倍率 同长度首句的首音延迟 工程修正后
服务器 N2 1× 1.26 s —
RK3566 4–5× 5.0–6.3 s 6–9 s
RK3528 6–8× 7.6–10.1 s 9–14 s

这是“首句仍为 16 字”的情况。产品上可以把首句压到 6–10 字，首音延迟约可降到 1/2–1/3；但在 RK3528 上仍需 3–6 s，体验不可接受。首音延迟和整段 RTF 必须一起优化，不能只看 RTF。

5.5 关键判断【外推】

  1. MeloTTS fp32 在 RK3566 / RK3528 上都不能直接实时。RK3566 更接近，RK3528 差距明显。
  2. 差距主要来自原始单核算力、缓存和内存带宽，不是 INT8 指令集——本次跑的是 fp32，服务器和盒子都没有用上 INT8 加速。
  3. 内存同样是硬约束：峰值 436 MB，对 1–2 GB 的盒子偏高；即使 RTF 勉强达标，内存和热降频也可能让体验不达标。
  4. 必须真机复测：以上全部是外推，不能作为采购/量产定论；真机数据是下一阶段的第一优先级。

5.6 端侧目标建议

指标 服务器实测 端侧目标 说明
整句 RTF 0.47–0.52 ≤0.5 留约 50% CPU 给 ASR、播放、系统
首音延迟 1.26 s ≤1.5 s 首句控制在 10–15 字
峰值内存 436 MB ≤200 MB 1–2 GB 盒子可承载
模型体积 163 MiB ≤60 MB 便于 OTA 与存储
模型加载 3.04 s ≤1.5 s 冷启动体验

六、RTF 优化方法

6.1 杠杆排序总览

优先级 手段 预期收益 代价 / 风险 适用平台
P0 换更轻的基座模型（Matcha / Piper / aishell3） 2–5× 音质、中文支持、许可需逐个验证 全部
P0 降低采样率（44.1 → 22.05 / 16 kHz） 1.3–2× 需模型原生支持，不能只对输出重采样 全部
P0 流式按句合成 + 预烘焙固定话术 不降总 RTF，但首音延迟大幅下降、实时负载下降 断句、衔接、并发工程 全部
P1 INT8 量化 A55 1.2–1.5×；A53 收益有限 音质、算子支持、需真机验证 RK3566 更有意义
P1 运行时/后端优化（C++/JNI、NCNN/MNN、线程绑核） 1.1–1.3× 工程量，收益有限 全部
P2 RK3566 NPU 卸载（预研，约 0.8 TOPS） 潜在 2–5× VITS 动态 shape/算子覆盖差，转换风险高 仅 RK3566
P2 蒸馏 / 剪枝定制小模型 2–3× 数据、训练、评测周期长 中长期
P0 控制 LLM 回复长度、缓存常见回答 降低实时合成时长 产品策略 全部

结论先行：换模型/降采样率是最高杠杆；量化与运行时是配角；流式是产品体验的放大器，但不能把 RTF>1 变成实时。

6.2 模型层（最高杠杆）

（1）降低采样率

  • 44.1 kHz 对盒子的小喇叭是“过度配置”，22.05 kHz 甚至 16 kHz 已足够。
  • 采样率降低会直接减少 vocoder 的输出样本数、decoder 的上采样计算和内存带宽，预期整体 1.3–2×。
  • 注意：不能简单把 44.1 kHz 输出重采样成 16 kHz——那不会减少计算。必须使用原生低采样率训练/微调的模型。

（2）换更轻的基座

候选 预期收益 优点 风险
Matcha-icefall-zh-baker 2–4× 非自回归、2-step flow + vocos，弱核友好；22.05 kHz 需实测音质与算子支持；包内 LICENSE 需复核
Piper zh_CN（x_low/low） 3–5× 为树莓派设计，20–60 MB，16/22.05 kHz 部分音色 CC-BY-NC，必须逐包核实
vits-icefall-zh-aishell3 3–5× 29 MB、Apache-2.0、最轻 8 kHz 音质偏低，适合做“速度上界”对照
Kokoro（中文） 待测 非自回归、24 kHz、Apache-2.0 82M 参数对 A53 可能仍偏重

建议：下一轮先并行实测 aishell3（速度上界）与 matcha-icefall-zh-baker（速度/音质平衡），再决定是否投入 Piper 的许可审查。

（3）蒸馏 / 剪枝

  • 用 MeloTTS 或 Matcha 作为教师，蒸馏一个更小的单说话人中文模型；
  • 预期 2–3×，但需要数据、训练和 MOS 评测，周期以月计；
  • 适合作为“没有现成模型满足 RK3528”时的兜底方案。

6.3 量化与精度

（1）INT8 动态量化

  • 当前 model.int8.onnx 是 133 字节占位 stub，不可用；需要官方 int8 模型或用 onnxruntime.quantization 重新量化。
  • 收益：
    • 模型体积约 4× 下降（163 MiB → 约 41 MiB），内存占用显著下降；
    • RK3566（A55，ARMv8.2 dotprod）：矩阵乘/卷积可得 1.2–1.5× 整体加速；
    • RK3528（A53，ARMv8.0 无 dotprod）：INT8 主要降低内存带宽，速度收益可能只有 1.0–1.1×，不要期待质变。
  • 风险：量化噪声、算子回退、音质下降；必须做 ABX/MOS 评测和真机验证。

（2）FP16

  • A55/A53 没有可用的 FP16 算术加速，不建议在端侧走 FP16。

（3）NPU（仅 RK3566）

  • RK3566 有约 0.8 TOPS INT8 NPU，理论上可卸载部分算子；
  • 但 VITS 包含动态 shape、flow、vocoder 上采样等，RKNN 的算子覆盖和转换成功率是主要风险；
  • 建议作为 P2 预研，不作为主路线；RK3528 无 NPU，不适用。

6.4 推理运行时与后端

  1. Android 原生 C++/JNI：使用 sherpa-onnx 官方 AAR/JNI，去掉 Python 解释器与胶水层开销；预期 1.05–1.15×，但这是产品化的必经之路。
  2. onnxruntime 会话调优：
    • graph_optimization_level=ALL；
    • intra_op_num_threads=4、inter_op_num_threads=1；
    • 开启 CPU memory arena，关闭 profiling；
    • 线程绑定 4 个可用核，并将 CPU governor 设为 performance。
  3. NCNN / MNN / XNNPACK：面向 ARM 的轻量后端，部分算子可能更快；预期 1.1–1.3×，需逐个验证 VITS 算子支持。
  4. 文本前端：词典、jieba、FST 只加载一次；缓存重复文本的分词/音素化结果。对短句的固定开销有帮助，但对长句 RTF 影响很小。

6.5 流式与产品架构（体验杠杆）

  1. 按句流式合成：在 。！？； 处切句，首句控制在 10–15 字；合成一句、播放一句，下一句在播放期间合成。
  2. 双缓冲/多缓冲：音频队列按序播放；新一轮对话开始时取消旧队列，避免叠音。
  3. 预烘焙固定话术：唤醒语、错误提示、常见问答（“我在”“网络未连接”“请再说一遍”）直接播放缓存音频，不经过实时 TTS。这类内容可覆盖相当比例的固定播报，具体比例需按产品话术统计。
  4. 控制 LLM 输出：限制回答长度、要求简洁口语化、规范标点；减少连续长段合成。
  5. 缓存常见回答：天气、时间等高频回答可缓存音频；注意失效策略。
  6. 语速微调：speed=1.05–1.1 可缩短音频时长、减少用户等待，但 RTF 会因分母变小而略升；它不是 RTF 优化手段，需与自然度一起评估。

流式不能把单句 RTF>1 变成实时；它的价值是把首音延迟从“整段”降到“首句”，并在单句 RTF<1 时让播放连续。

6.6 系统工程

  • CPU 可用性：Android 后台限制、前台服务、线程亲和性都会影响 4 核是否真正可用；需在真机上确认。
  • 热设计：无风扇盒子持续 4 核推理会降频；需测量 10 分钟持续 RTF，不能只看冷启动。
  • 内存预算：目标峰值 ≤200 MB；当前 436 MB 对 1–2 GB 盒子偏高。INT8 + 更小模型是主要手段。
  • 存储/OTA：163 MiB 模型需考虑首次下载、压缩、A/B 升级和存储余量。
  • 功耗：4 核持续推理的功耗/发热可能超出盒子电源预算，需与硬件团队联合评估。

6.7 组合效果测算【建议，非实测】

以“端侧 RTF≤0.5”为目标，按乘性收益粗略估算（实际收益会重叠，需实测）：

场景 基线 RTF 组合手段 合计收益 估算 RTF 判断
RK3566 2.3–3.4 22.05 kHz（1.5×）+ 轻量模型（2.5×）+ INT8（1.3×）+ 运行时（1.1×） 约 5.4× 0.43–0.63 有希望达标；需真机验证
RK3566（不换模型） 2.3–3.4 仅降采样 + INT8 + 运行时（约 2.1×） 约 2.1× 1.1–1.6 不达标；换模型是必选项
RK3528 3.4–5.3 16 kHz（2×）+ Matcha/Piper（3.5×）+ INT8（1.1×）+ 运行时（1.1×） 约 8.5× 0.40–0.63 理论可达标，但依赖更激进的模型替换
RK3528（仅量化/运行时） 3.4–5.3 降采样 + INT8 + 运行时（约 2.4×） 约 2.4× 1.4–2.2 不达标

结论：

  • RK3566：保留“较好音质”的前提下，通过 22.05 kHz + 轻量模型 + INT8 + 运行时优化，有机会把 RTF 压到 0.5 附近，是更现实的首发硬件。
  • RK3528：必须使用 16 kHz + Matcha/Piper 级轻量模型，且收益估算偏乐观；如果音质不能妥协，建议 RK3528 不做本地实时 TTS，或改为“预烘焙话术 + 云端 TTS 兜底”的产品策略（与“纯本地”定位冲突，需产品决策）。
  • MeloTTS 的定位：音质基线 / 服务器演示 / 可在 RK3566 上做非实时预生成并缓存；不作为 RK3528 的默认实时模型。

八、风险与未验证项

风险 说明 应对
服务器数据偏乐观 N2 的 IPC、缓存、内存带宽远强于 A55/A53 所有端侧结论以真机复测为准
RK3528 规格不确定 公开资料主频 1.5–1.8 GHz 不一 以实际板子为准，本文按 1.5 GHz 保守估算
